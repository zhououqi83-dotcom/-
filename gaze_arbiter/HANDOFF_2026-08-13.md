## 一、当前卡住的问题（最需要关注）

**现象**：用户说"机器人一直没有盯着我"——人一直站在摄像头范围内，但机器人
头部感觉没有转动/没有明显反应。

**已排查、确认不是问题的部分**（软件链路本身看起来是对的）：

1. 摄像头确实检测到了人脸（网页画面有红框，`/state` 接口 `people` 数组
   非空）。
2. 检测到的 `yaw_deg`（人脸在画面里的方位角）数值合理，会随人移动变化，
   例如实测样本：`yaw_deg=-36.6° → -30.6° → -36.1° → -37.2°`。
3. `head_yao`（舵机归一化值）会跟着 `yaw_deg` 变化，且用公式反推数值对得
   上（`yaw=-7.44°` 时期望 `frac≈0.558`，实测 `head_yao=0.548`，基本吻合，
   `HEAD_INVERT=1` 默认开启已经算进去了）。
4. 观察到过 `head_yao` 从 `0.5`（正中）变化到 `0.79` 这种量级的样本——
   按 `min_frac=0.15 / max_frac=0.85` 的可用行程算，这是舵机总行程的
   **~30%**，理论上肉眼应该能看出转动。
5. 之前（今天早些时候，见下面第二节）已经用不接摄像头的纯净脚本直接给
   `NaturalHeadDriver` 喂固定角度/自然摆动，在**同一个物理机器人**上验证
   过舵机确实会转（gRPC 服务端日志里能看到 `SetHeadState` 数值连续变化，
   见 `/tmp/claude-1000/run_with_head_natural.log`、
   `/tmp/claude-1000/head_grpc_gaze_arbiter*.log`）。

**还没排查的方向**（下一步建议从这里入手）：

- 会不会是**这次真人摄像头场景下**触发了 `NaturalHeadDriver` 里某个之前
  没覆盖到的边界情况？比如目标 `person_id` 频繁切换（真实检测比模拟数据
  噪声大很多，`track_id` 一直在变——今天样本里见过 `track_id` 从 `67` 跳到
  `78` 又跳到 `124`）导致 saccade 一直被打断、或者卡在某个奇怪的中间态。
  **建议**：在 `NaturalHeadDriver.update()` 里加日志或者写一个更贴近真实
  场景的压力测试（`yaw_deg` 高频抖动 + `person_id` 频繁切换，模拟真实检测
  的噪声特征），而不是像现有测试那样用干净的固定值。
- 会不会是**物理硬件/控制权**问题？虽然 `head_error` 一直是 `null`（没报
  错），但没有直接确认"网页发出的 `set_servo_positions` 调用" 和"物理舵机
  真的收到并执行"这两件事在**这次真人测试的时间窗口内**是一致的——之前
  验证硬件是好的是在另一次独立连接里做的，中间该连接已经断开重连过很多次
  （见下面故障排查历史），不能 100%排除这次连接状态本身有问题（比如
  `head_client.release_control()` 没生效、控制权被别的客户端占着）。
  **建议**：用户在物理现场时，同时看 `head_grpc_server.py` 的终端输出
  （应该能看到 `SetHeadState: {...}` 持续刷新），跟网页 `/state` 接口的
  `head_yao` 字段做实时对照，确认"软件说在转"和"gRPC 服务端收到指令"是否
  一致；如果服务端也在收到指令但舵机物理不转，那就是硬件/接线问题，不是
  这次改的代码的问题。
- 幅度问题：真实人脸检测给出的 `yaw_deg` 大部分时候可能就是个位数到十几度
  （人不会站到画面边缘），换算成舵机行程的视觉转动幅度可能确实比较小，
  用户"感觉没转"也可能只是**主观上没注意到小幅转动**，而不是没转。建议
  让用户明确走到画面左右两侧边缘，确认那种大幅度（`yaw` 三四十度）情况下
  是否有肉眼可见的转动，缩小问题范围。

### 2.2 gaze_arbiter 项目本身

`gaze_arbiter` 是一个独立的"多人场景该看谁"注视决策系统，详见
`PLATFORM.md`。今天做的事：

1. **新写了 `natural_motion_reference.py`**：把 exp_deb 自然状态实际在用
   的参数（眨眼/呼吸/漂移/注视限位等）整理成引用模块，给 gaze_arbiter 调参
   时对照，纯数据，不改变任何行为。

2. **给 `HeadDriver`（旧版 EMA+限速驱动）加了 `idle_sway`**：没人被注视时
   带一点低幅度自然摆动，而不是完全僵住。加了网页按钮（"开启自然摆动"）、
   环境变量（`HEAD_IDLE_SWAY` 等）。**这一版工作正常**，用纯净脚本 + 真实
   硬件验证过（不接摄像头，直接喂 `yaw_deg=None`，舵机确实做出了正弦摆动）。

3. **新写了 `natural_head_driver.py`（`NaturalHeadDriver`）**：这是今天的
   重头戏。用户要求"让 gaze_arbiter 的转头手感和 exp_deb 自然状态一样"。
   原来的 `HeadDriver` 是 EMA+限速（照抄声源追踪那套逻辑），新的
   `NaturalHeadDriver` 改用 droidmotion 那套 **min-jerk 钟形曲线 saccade**
   （Carpenter 1988 时长公式 + min-jerk 形状函数），小于 `pursuit_max_deg`
   （默认 5°）的漂移不重启轨迹。**没有 import droidmotion**（gaze_arbiter
   刻意保持零重依赖），是照抄同样的数学公式重新实现的。

   `web_dashboard.py`、`run_with_head.py`、`run_with_head_fake.py` 三个
   入口全部从 `HeadDriver` 切到了 `NaturalHeadDriver`。

4. **过程中发现并修了两个真 bug**（都在 `natural_head_driver.py` 里，都是
   今天新代码引入的，不是历史遗留）：

   - **Bug A**：自然摆动(`idle_sway`)的触发条件里错误地要求
     `self._traj is not None`（必须先真实追踪过一次目标才允许摆动），导致
     刚连接、还没检测到过人时摆动完全不生效。**已修复**：去掉这个多余条件，
     围绕 `_last_real_yaw` 默认值（0.0，正前方）摆动。用纯净脚本+真实硬件
     验证过（幅度 15°，`sent_frac` 范围 `0.383~0.617`，明显摆动）。

   - **Bug B（更严重）**：目标漂移小于 `pursuit_max_deg`（5°）时，代码是
     **完全忽略**这次更新，而不是继续小幅跟随。如果人是缓慢连续移动（每帧
     增量都在 5° 以内，但累计起来幅度不小），头会永久锁死在第一次稳定的
     位置——这正是"人脸追踪功能感觉消失了"的根因。**已修复**：加了一层
     "平滑微跟随"（模拟 droidmotion 里眼球 VOR 做的 smooth pursuit，指数
     逼近 + `pursuit_tau_s` 时间常数，默认 0.15s），已经稳定后遇到小幅漂移
     会持续柔和跟随，只有真正大幅跳变才触发新的快速转头。

   两个 bug 都补了单元测试（`tests/test_natural_head_driver.py`，共 8 个
   测试），当前**全部 73 个测试通过**（`gaze_arbiter/venv/bin/python -m
   pytest tests/ -q`）。

5. **修完两个 bug、重启网页服务后，用户反馈"还是不会转头"**（也就是本文档
   第一节在排查的问题）。我做了几轮实时数据采样(`/state` 接口)和一次画面
   截图核实，**目前看到的数据本身是合理的、跟公式对得上**，但用户仍然表示
   现实中没看到机器人头明显转动。目前卡在这里，需要接手的人从物理现场
   （能看到真实机器人）继续核实"软件确实发出了指令"和"舵机物理执行了指令"
   这两件事之间到底哪一环出了问题，或者是不是幅度太小被主观忽略了。
