# 声音追踪头部转动 使用说明

用 J7034G4 麦克风阵列板测声源方向，让机器人头(`head_yao` 舵机)自动转过去追踪声音。脚本：`sound_track_head.py`。

---

## 整体架构

```
[J7034G4 麦克风阵列板]          [头部舵机控制板]
        ↕ 串口(USB)                    ↕ 串口(USB, /dev/ttyACM0)
        │                       [head_grpc_server.py]  ← 终端1, gRPC :2543
        │                               ↕ gRPC(网络, 可跨 Windows/WSL)
        └──────────→ [sound_track_head.py] ──────────────┘
                 读 doa_angle → 换算角度 → 发 head_yao 目标位置
```

`sound_track_head.py` 同时做两件事：
1. 读 J7034G4 串口的 `doa_angle = X`（0~180°，与 `sound_localization/pc_tool/j7034g4_monitor.py` 是同一块板子、同一种协议）
2. 通过 `head_sdk.HeadSDK` 把角度换算成 `head_yao`（摇头/左右摆动）舵机目标位置发出去

---

## 前提条件

- 终端1：`head_grpc_server.py` 已经在跑（跟 `使用说明.md` 里说的一样）：
  ```bash
  conda activate face_servo
  cd servo_tuning/head-sdk-face/head-server/src
  python head_grpc_server.py --config servoConfig_25DV3_Ula.yaml
  ```
- J7034G4 麦克风阵列板已经用 USB 接到电脑上

## 两种部署方式

**这两种方式跑的是同一份脚本，只是"J7034G4 从哪读"不一样，二选一即可。**

### 方式 A：全部在 Windows 原生跑（推荐，更稳）

J7034G4 直接读 Windows 的 COM 口，`head_sdk` 通过网络连 `head_grpc_server.py`（不管它是在本机还是 WSL 里跑，只要网络通）。

**一次性环境准备**（用专门建的 venv，不装进 Anaconda 免得冲突）：
```powershell
# 已经建好在 D:\droidproject\mic_gauge_venv，装的包括：
#   matplotlib numpy pyyaml pyserial grpcio protobuf
#   head_sdk（从 servo_tuning/head-sdk-face/head-sdk 装，--no-deps 装避免版本冲突）
#   rena2_sdk_api（从 head-sdk 目录下的 whl 装，同样 --no-deps）
```

**运行：**
```powershell
D:\droidproject\mic_gauge_venv\Scripts\python.exe D:\droidproject\servo_tuning\sound_track_head.py --mic-port COM8 --host 127.0.0.1 --gui
```

> `--host 127.0.0.1` 能用是因为 WSL2 有个"localhost 转发"功能：只要 `head_grpc_server.py` 监听的是 `0.0.0.0`（默认就是），Windows 访问 `127.0.0.1:2543` 会自动转发进 WSL，不需要查 WSL 的虚拟网卡 IP。

### 方式 B：全部在 WSL 里跑（需要 USB 直通，稳定性较差）

把 J7034G4 这个 USB 设备通过 `usbipd` 直通进 WSL，两边都在 WSL 里跑。

**已知问题：跑一段时间后麦克风会"突然没信号"**，dmesg 里能看到大量 `vhci_hcd: urb->status -104`（USB/IP 隧道连接被重置）。这是 `usbipd` 这种"USB 设备网络化转发"方案在**持续高频串口读取**场景下的已知短板，不是代码或硬件问题。遇到时按下面"常见问题"里的方法重连，或者干脆换回方式 A。

**一次性环境准备（Windows 端，管理员 PowerShell）：**
```powershell
usbipd list                              # 查 J7034G4 的 busid（举例是 2-6）
usbipd bind --force --busid 2-6          # 只需做一次
usbipd attach --wsl --busid 2-6          # 每次要用之前都要 attach 一次
```

**运行（WSL 里）：**
```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY \
  ~/venvs/sound_track_head/bin/python /mnt/d/droidproject/servo_tuning/sound_track_head.py \
  --mic-port /dev/ttyUSB0 --host 127.0.0.1 --gui
```

> `env -u ...` 那段必须加：这台机器全局设了 HTTP 代理，会导致 grpc 连接失败（no_proxy 的通配符规则 grpc 不认，`127.*` 这种写法它识别不了），必须显式清掉代理环境变量。

## 命令行参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--mic-port` | `COM7` | J7034G4 串口号（Windows 是 `COM8` 这种，WSL 是 `/dev/ttyUSB0` 这种，具体看现在接的是哪个，别直接抄默认值） |
| `--mic-baud` | `115200` | J7034G4 波特率 |
| `--host` | `127.0.0.1` | `head_grpc_server.py` 所在地址 |
| `--sdk-port` | `2543` | gRPC 端口 |
| `--gui` | 关闭 | 打开图形化仪表盘（见下）；不加就是纯文字刷屏 |
| `--invert` | 关闭 | 头转的方向跟声源反了就加这个 |
| `--offset-deg` | `0` | 头"正对前方"跟 J7034G4 的 0° 基准没对齐时的角度微调 |
| `--min-frac` / `--max-frac` | `0.15` / `0.85` | `head_yao` 归一化范围，别设到 0~1 满量程，避免撞硬限位 |
| `--rate-hz` | `12` | 发指令频率 |
| `--smoothing` | `0.25` | 指数平滑系数（0~1），越小越平滑但越滞后（滤的是读数噪声，不限制转动速度） |
| `--max-speed` | `0.6` | 头部转动最高速度，单位：`head_yao` 归一化值/秒（限制舵机实际移动速度的硬上限，声源方向突变时头不会猛地甩过去）。默认配合 `--min-frac`/`--max-frac`（区间宽 0.7）大约是"从一头转到另一头要 1.2 秒"；嫌转得太快就调小 |
| `--stale-s` | `2.0` | 超过这么久没收到新 `doa_angle` 就停止发指令，头停在原地 |

## 图形化界面（`--gui`）

极坐标仪表盘，跟 `sound_localization/pc_tool/j7034g4_monitor.py` 是同一个画法，多叠了一根指针：

- **红色指针**：J7034G4 测到的声音方向（`doa_angle` 原始读数）
- **蓝色指针**：头当前**真实**转到的角度（从 `HeadSDK` 后台状态同步线程读的实际舵机位置，不是发出去的目标值——舵机卡住/没跟上也能如实反映）
- 下方文字：`声音 doa=xx°   头部 head_yao=0.xx`

正常情况下红指针先动、蓝指针追过去，最后两根重合。

## 首次使用要标定的两件事

1. **方向反了**：对着板子左边发声，头却转向右边 → 加 `--invert`
2. **中心没对齐**：头默认朝向（`head_yao=0.5`）跟 J7034G4 的"90°"（一般是正对板子中垂线方向）没对上 → 用 `--offset-deg` 微调，正负试出来

## 常见问题排查

| 现象 | 原因 | 解决方法 |
|---|---|---|
| `ModuleNotFoundError: No module named 'serial'` | 用错了 Python 环境（比如在 WSL 里跑但脚本要读 Windows 的 COM 口） | 确认方式 A 用 Windows venv 的 python，方式 B 用 WSL venv 的 python，别混 |
| `✗ 连不上头部舵机服务` | 终端1的 `head_grpc_server.py` 没在跑，或者 `--host`/`--sdk-port` 填错 | 检查终端1还活不活；Windows 连 WSL 用 `127.0.0.1`，两边同一台 WSL 才对 |
| grpc 报 `Socket closed` / 连 `127.0.0.1:7890` 失败 | 全局 HTTP 代理把 grpc 连接劫持了 | 加 `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY`（WSL）或检查 Windows 环境变量代理设置 |
| 跑一段时间后"突然没信号"（方式 B） | USB/IP 隧道不稳，dmesg 里有 `urb->status -104` | 详见下一行 |
| 上面这个问题的重连方法 | — | Windows 管理员 PowerShell：`usbipd detach --busid <id>` 再 `usbipd attach --wsl --busid <id>`；反复出现就换方式 A |
| 从 WSL 切回方式 A 后，Windows 设备管理器里还是看不到 COM 口 | `usbipd bind`（尤其加了 `--force`）会把设备换成 usbip 的桩驱动，光 `detach` 不够，驱动关联还在 | 管理员 PowerShell 再跑一次 `usbipd unbind --busid <id>`，彻底还给 Windows 原生驱动。之后 COM 号可能会变，去设备管理器重新确认 |
| `usbipd list` 里这个设备整个消失了（不是 Not shared，是完全不见了） | bind/unbind/attach/detach 来回切换后 USB 设备卡进了坏状态 | 物理拔插一次 J7034G4 的 USB 线，让它重新走一遍枚举 |
| 头转的方向跟声音反着 | 麦克风阵列摆放方向 / 舵机方向跟假设的不一致 | 加 `--invert` |
| 头一直卡在中间不太动 | `--min-frac`/`--max-frac` 区间太窄，或者 `--smoothing` 太小反应太慢 | 适当放宽区间、调大 `--smoothing` |
| 头转得太猛/太快，动作生硬 | 没限制转动速度（旧版本）或 `--max-speed` 设太大 | 调小 `--max-speed`（比如 0.3），数值越小转得越慢越平稳 |
| COM 口对不上（比如脚本报串口打不开） | Windows 重新分配了 COM 号 | 设备管理器里查"USB-SERIAL CH340"当前对应的 COM 号，改 `--mic-port` |
